StaffGlimpse uses a role-based access control (RBAC) model to govern what each employee can see and do inside the platform. Every user is assigned a `userRole` of either `ADMIN` or `USER`, and administrators can layer on top of that with custom roles that carry fine-grained, per-module permission matrices. This gives you the flexibility to tailor access for every team, department, and job function in your organisation.

## User Roles

Two built-in roles are available to every tenant:

<CardGroup cols={2}>
  <Card title="ADMIN" icon="shield-halved">
    Full access to company settings, user management, department and role
    configuration, attendance approval workflows, and leave policy setup.
    Admins can also create and manage custom roles.
  </Card>
  <Card title="USER" icon="user">
    Standard employee access. Users can punch in and out, submit leave
    requests, view and update their own profile, and access documents shared
    with them.
  </Card>
</CardGroup>

## Custom Roles

Admins can create additional roles to represent specific job functions or seniority levels within a department. Use `POST /company/role/create` to define a new role:

```bash
POST https://r00buwtnh1.execute-api.ap-south-1.amazonaws.com/live/company/role/create
Authorization: Bearer <AWS_Cognito_ID_Token>
x-api-key: <static_shared_key>
Content-Type: application/json
```

```json
{
  "roleName": "Team Lead",
  "description": "Leads a squad within the Engineering department",
  "departmentId": "dept_01HXYZ",
  "equivalentRolePosition": 2
}
```

Each custom role carries the following properties:

<AccordionGroup>
  <Accordion title="roleName" icon="tag">
    A human-readable label for the role, shown throughout the dashboard and in
    API responses (e.g., `"Team Lead"`, `"HR Manager"`).
  </Accordion>
  <Accordion title="description" icon="align-left">
    A free-text description of the role's responsibilities. Useful for keeping
    your role catalogue self-documenting.
  </Accordion>
  <Accordion title="departmentId" icon="building">
    Associates the role with a specific department. Obtain valid department IDs
    from `GET /company/department/get`.
  </Accordion>
  <Accordion title="equivalentRolePosition" icon="arrow-up-1-9">
    A numeric rank that establishes hierarchy among custom roles within a
    department. Lower numbers represent more senior positions.
  </Accordion>
</AccordionGroup>

## The Permissions Matrix

Every role — built-in or custom — has an associated permissions matrix that defines exactly what actions users assigned to that role can perform on each module. Retrieve a role's current matrix with:

```bash
GET https://r00buwtnh1.execute-api.ap-south-1.amazonaws.com/live/company/role/permissions/get?roleId={roleId}
Authorization: Bearer <AWS_Cognito_ID_Token>
x-api-key: <static_shared_key>
```

The matrix is returned as an array of module permission objects inside `result`:

```json
[
  {
    "module": "holidays",
    "read": true,
    "write": false,
    "create": false,
    "delete": false,
    "import": false,
    "export": false
  },
  {
    "module": "attendance",
    "read": true,
    "write": true,
    "create": false,
    "delete": false,
    "import": false,
    "export": true
  }
]
```

The six permission flags that can be toggled per module are:

| Flag     | Controls                                              |
| -------- | ----------------------------------------------------- |
| `read`   | Viewing records and details for this module           |
| `write`  | Editing or updating existing records                  |
| `create` | Creating new records from scratch                     |
| `delete` | Permanently removing records                          |
| `import` | Bulk-importing data (e.g., via CSV upload)            |
| `export` | Exporting data to downloadable files                  |

## Updating Permissions

To update the permissions matrix for a role, call `PUT /company/role/permissions/update` and supply the `roleId` along with the complete permissions array. Partial updates are not supported — always pass the full matrix to avoid inadvertently revoking access:

```bash
PUT https://r00buwtnh1.execute-api.ap-south-1.amazonaws.com/live/company/role/permissions/update
Authorization: Bearer <AWS_Cognito_ID_Token>
x-api-key: <static_shared_key>
Content-Type: application/json
```

```json
{
  "roleId": "role_01HABC",
  "permissions": [
    {
      "module": "holidays",
      "read": true,
      "write": true,
      "create": true,
      "delete": false,
      "import": false,
      "export": false
    }
  ]
}
```

<Warning>
  Always pass the **full** permissions array when calling
  `PUT /company/role/permissions/update`. Any modules omitted from the array
  will be reset to all-false, potentially locking users out of features they
  previously had access to.
</Warning>

## Checking User Count

Before deleting a role, verify that no employees are still assigned to it. Use the user count endpoint to check:

```bash
GET https://r00buwtnh1.execute-api.ap-south-1.amazonaws.com/live/company/role/users/count?roleId={roleId}
Authorization: Bearer <AWS_Cognito_ID_Token>
x-api-key: <static_shared_key>
```

The response returns the number of users currently holding the specified role. Reassign those users before proceeding with deletion to avoid orphaned accounts.

<Note>
  Permissions are enforced server-side on every request. Even if your client
  application skips a permission check, the API will still reject unauthorised
  operations and return a `403 Forbidden` error. Never rely on client-side
  permission checks as your only gate.
</Note>
